### 0.3 배경 컨텍스트

**3/25 콘텐츠 프롬프트 시스템 통합 미팅 결정 사항:**
- 캐스팅 이미지 생성: 프론트에서 사용자 선택 키워드를 영어로 전달 → 백엔드에서 키-밸류 매핑으로 프롬프트 조합.
- 콘텐츠 이미지 생성(daily/school/finger): 각 프롬프트 블록(장소, 시선, 표정, 의상, 카메라 등) 내 경우의 수를 백엔드에서 랜덤 선택하여 조합.
- 레퍼런스 이미지: 멤버 아이디 기반으로 DB에서 캐스팅 이미지 조회하여 모델에 전달.
- 이미지 생성 모델: `gemini-3.1-flash-image-preview`
- UI 표현 방식(드롭다운/버튼)은 추후 결정, 현재는 키워드 확정에 집중.

## 1. 시스템 통합 구조 (3/25 미팅 결정 사항 반영)

### 1.1 캐스팅 이미지 — 키워드 매핑 방식

3/25 미팅에서 확정된 구조:

```
[프론트엔드] 사용자가 칩 선택 (한국어)
     ↓ 영어 키워드 전달 (예: "chic", "sharp_features", "black_short")
[백엔드] 키-밸류 매핑으로 프롬프트 조합
     ↓ casting_variable_blocks.json 기반
[Gemini API] 최종 프롬프트 텍스트 전송
     ↓
[결과] 캐스팅 이미지 생성 → DB 저장 (멤버 ID 기반)
```

- 프론트에서 키워드만 전달, 백엔드에서 키-밸류 매핑으로 프롬프트 관리
- 프롬프트 변경 시 백엔드에서 일괄 관리 가능 (프론트 배포 불필요)

### 1.2 콘텐츠 이미지 — 랜덤 블록 선택 방식

3/25 미팅에서 확정된 구조:

```
[백엔드] 콘텐츠 타입별 옵션 블록 내 경우의 수를 랜덤 선택
     ↓ 예: fullbody의 Scene 2종 중 1개, Gaze 3종 중 1개, ...
[프롬프트 빌드] base_content_prompt.py 프레임워크로 조립
     ↓ IDENTITY_LOCK + 가변 블록 조합 + CONSTRAINT_LOCK
[Gemini API] 최종 프롬프트 + reference image(멤버 ID로 DB 조회) 전송
     ↓
[결과] 콘텐츠 이미지 생성
```

- 전신/4-Frame도 이 구조를 따를 예정 (확인 필요)

### 1.3 레퍼런스 이미지 파이프라인

| 단계 | 처리 | 비고 |
|------|------|------|
| 캐스팅 이미지 저장 | 멤버 ID 기반 DB 저장 | 저장 위치(GCS/S3/DB URL) 구체적으로 미확정 |
| 콘텐츠 생성 시 조회 | 멤버 ID로 캐스팅 이미지 DB 조회 | 대표 이미지 1장 선택 로직 필요 |
| API 전달 방식 | base64 vs URL 링크 | 미확정 — 제형과 추가 논의 필요 |

### 1.4 Sprint 6에서 추가로 논의할 시스템 이슈

3/25 미팅 안건에서 논의되었으나 아직 미확정인 사항:

| 이슈 | 현재 상태 | 필요한 결정 |
|------|----------|-----------|
| 콘텐츠 조합 저장 방식 | JSON 파일로 관리 중 (예: `daily_combinations.json`) | DB 테이블 vs JSON 파일. 콘텐츠 타입 늘어날 때 확장성 고려 |
| 프롬프트 빌드 위치 | 현재 `build_prompt()` 함수가 프롬프트 모듈 내에 존재 | 백엔드 직접 import vs 별도 서비스 분리 |
| API 엔드포인트 구조 | 미확정 | 콘텐츠 타입별 분리 (`/generate/fullbody`) vs 통합 (`/generate?type=fullbody`) |
